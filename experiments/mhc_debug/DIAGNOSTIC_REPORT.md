## 一、结论摘要

崩溃**不是**数据、学习率或超参问题，而是 **CANN 融合算子 `aclnnMhcPreSinkhornBackward`
（MHC 前置变换 + Sinkhorn 归一化算子的反向传播部分）的一个静默数值缺陷**：

1. 该算子的**前向在所有输入下始终正确**（误差在 bfloat16 存储精度地板内），所以崩溃前
   loss 曲线完全正常，毫无先兆；
2. 但它的**反向梯度在"残差连接头的 softmax 输入幅值"超过约 5 之后开始系统性错误**，
   超过约 20 后**梯度符号翻转、幅度错 10~74 倍**，且是有限值错误（不是 NaN），任何
   NaN 检查都拦不住；
3. MHC 参数是零初始化的，即 softmax 输入幅值从 0 出发，随训练中权重增长而逐渐跨过
   阈值——这解释了"为什么前 1000 步好好的、突然崩"；
4. 崩溃点精确定位在**第 1088 步**：loss 从 2.38 两步内跳到 11.7，梯度范数从 0.49 冲到
   195，此后永不恢复；
5. 用崩溃任务检查点里的**真实训练参数**直接对拍算子与双精度参考实现：饱和度最高的
   6 个模块梯度全部错误（最高错 34.5 倍且反号），饱和度为零的对照模块完全干净——
   剂量-响应关系成立，证据链闭环；
6. **根因已定位到算术精度层面**（2026-10-16，`decompose_pre_sinkhorn_bwd.py`）：
   算子的反向递推公式经源码逐行推演数学正确、前向保存给反向的中间量经逐槽对拍
   就是真值、把全真值保存量替换喂入也不改变错误输出；而按算子源码的**精确
   fp32 运算顺序**在 CPU 上重执行同一递推，能把它输出的错误梯度复现到 0.02%，
   同一递推用 fp64 执行则得到正确值——即**反向的 39 步"除-减"链在饱和（近
   one-hot）矩阵上发生 fp32 灾难性抵消，有效数字耗尽**。低饱和时矩阵近均匀、
   链条良态，fp32 干净——与全部剂量-响应观测吻合；前向只做除法无相减，故始终
   正确。

## 三、概念详解（读懂本报告所需的全部背景）

这一节把报告中用到的每个概念从零讲起。已经熟悉的读者可以直接跳到第四节。

### 3.1 MHC 模块在模型里做什么

MHC 是 deepseek4 主线实现里的一种**残差流混合机制**。普通 Transformer 每层只有 1 条
残差流；这个模型每层有 **4 条**（张量形状为 `[序列长度, 批大小, 4, 隐层维度]`），
每个注意力子层 / 多层感知机子层的前后各做一次 MHC 变换：

```
前置阶段（hc_pre）：  y    = Σ(e=1..4) pre_e  · x_e          ← 喂给子层的输入
子层计算：            res  = 子层(y)
后置阶段（hc_post)：  out_e = post_e · y + Σ(f=1..4) comb_e,f · res_f   ← 写回 4 条流
```

其中三组系数不是写死的超参，而是由一个**小线性层 `hc_fn` 从当前 4 条流动态算出**：

1. 先对输入做均方根归一化（每条流除以自己的均方根，见 3.4）；
2. 归一化后的向量与 `hc_fn.weight`（形状 24 × 4096）做内积，得到 24 路"混合系数"
   （下文称 mixes）；
3. 24 路 = 4 路 pre 门 + 4 路 post 门 + 16 路连接矩阵（4×4）；
4. `hc_scale`（3 个标量）和 `hc_base`（24 个标量）分别是三组 logit 的缩放与偏置：
   - `pre_e  = sigmoid(mixes_e · hc_scale[0] + hc_base_e) + ε`，取值 (0,1)，是保留门；
   - `post_e = 2 · sigmoid(mixes_e · hc_scale[1] + hc_base_e)`，取值 (0,2)，是写出门；
   - `comb   = softmax(mixes · hc_scale[2] + hc_base) 再做 20 轮 Sinkhorn 归一化`，
     是 4×4 的**双随机矩阵**（每行每列求和都为 1），可以理解为"软置换"——把 4 条流
     近似重新排列组合后写回。

Sinkhorn 归一化就是反复交替地"每行除以行和、每列除以列和"，多轮后矩阵逼近双随机。
这是把"可学习的任意矩阵"约束成"接近置换矩阵"的标准做法。

参数量：每个模块 24×4096 + 24 + 3 ≈ 9.8 万；全模型 **56 个模块**（28 层 ×
注意力/多层感知机各 1 个），另有 1 个 `hc_head` 头部模块（见 6.7）。

### 3.2 融合算子与 `use-fused-mhc` 开关

同一套数学，仓库里有两条实现路径（`mindspeed_llm/tasks/models/transformer/deepseek4/mhc.py`）：

| 开关 | 路径 | 说明 |
| --- | --- | --- |
| `use-fused-mhc: false` | 逐条 torch 公式（eager 模式） | 代码里显式 `.float()`，即**自动转单精度浮点计算**，慢但已被本诊断验证数值干净 |
| `use-fused-mhc: true` | 调 CANN 内置融合算子 | `aclnnMhcPreSinkhorn`（前置+Sinkhorn）与 `aclnnMhcPost`（后置），模块级快约 5 倍 |

**崩溃任务用的是 `true`（融合算子路径）。** 出问题的只是前置算子的反向传播部分
（`aclnnMhcPreSinkhornBackward`）；后置算子 `aclnnMhcPost` 经全面测试无嫌疑（见 4.1）。

### 3.3 "饱和"是什么，为什么饱和会暴露数值实现的缺陷

`sigmoid(z)` 和 `softmax(z)` 这类函数的特性：

- z 接近 0 时，输出对输入很敏感，曲线陡；
- |z| 变大（比如超过 5）时，sigmoid 输出贴住 0 或 1，softmax 输出接近 one-hot
  （一个分量是 1，其余是 0）——这就叫**饱和**。

饱和在数学上没有错（导数趋近 0 是真实性质），但对**数值实现**非常苛刻：

- 反向传播需要计算 `sigmoid 的导数 = sigmoid · (1 - sigmoid)`，深饱和时这是两个极小
  数相乘；
- softmax 反向涉及 `p_i · (δ − p_j)` 这类**相互抵消的差项**，p 贴 0/1 时有效数字
  大量丢失；
- 工程实现通常还有最大值平移、指数裁剪等防护逻辑，任何一处写得不够精细，**常规域
  （z 小）完全看不出来，深饱和区（z 大）误差爆炸**。

本报告用 **logit 幅值 |z| 来量化饱和程度**：|z| ≤ 4 算未饱和，5~7 轻度饱和，
≥ 20 深饱和（softmax 实际上已经是 one-hot）。

### 3.4 z_res 与 zmax_est 公式的逐项含义

"res 头"指连接矩阵 comb 那 16 路（3.1 的第三组）。它的 softmax 输入是：

```
z_res = mixes_res · hc_scale[2] + hc_base[后16个]
      = (归一化后的激活 · hc_fn.weight 后 16 行的内积) × s2 + b2
```

为书写简便，下文记 `s2 = hc_scale[2]`（1 个标量）、`b2 = hc_base 后 16 个`、
`W_res = hc_fn.weight 的后 16 行`。**z_res 的幅值就是该模块的饱和度。**

检查点里只有权重、没有当时的激活，怎么估计 z？关键在于：**算子内部会先对输入做
均方根归一化**（代码 `rsqrt(x²·mean + ε)`），归一化之后每条流每个维度的典型幅度
就是 1，与激活原始大小无关。一个单位尺度的向量与权重矩阵某一行的内积，其典型幅度
约等于**该行的欧氏范数** ‖W 行‖。因此：

```
zmax_est = |s2| · max‖W_res 各行的范数‖ + max|b2|
```

含义：**该模块 res 头 softmax 输入在全部序列位置上的最大幅值的估计**——

- `|s2|`：缩放标量的绝对值（崩后实测全部在 1 以内，中位数 0.21）；
- `max‖W_res 行‖`：hc_fn 后 16 行中最大的行范数（**z 的增长主要来自它**——训练中
  hc_fn 权重长大，行范数变大）；
- `max|b2|`：偏置项贡献的固定平移。

这个估计**只看权重、不依赖激活**（整体缩放被归一化吃掉了），跨模块排序可靠；真实
激活与权重有相关性时会有出入，但第五节用"真实参数直接对拍"验证了排序完全正确。
它好算到可以在训练中当监控指标用（见 7.3）。

### 3.5 梯度对拍怎么读（误差指标定义）

诊断的核心方法是**对拍**：把同一批输入同时喂给"被测实现"和"参考实现"，比较输出。

- **双精度参考实现**：在 CPU 上用 float64（约 16 位有效数字）把 3.1 的公式逐条复现。
  喂给它的是算子实际吃到的**同一批已量化的张量值**（不是重新采样），所以两者的任何
  差异都可归因于被测实现内部；
- **相对误差** = max|被测 − 参考| / max|参考|：逐点最大误差的归一化，1e-4 就是
  "最差的点错了万分之一"；
- **系统性偏置** = mean(被测 − 参考) / mean|参考|：误差若随机，此值接近 0；若它
  接近相对误差本身，说明误差**方向一致**。对训练最致命的正是这种——所有梯度齐心
  往同一个错误方向推参数；
- **bfloat16 地板**：训练激活是 bfloat16（8 位尾数），相对 3e-3 以内的误差是存储
  精度本身造成的，不算缺陷。单精度浮点（float32，23 位尾数）的地板约 1e-6~1e-4；
- 下文的 `对 s2 的梯度` 指损失函数对 `hc_scale[2]` 这个标量的梯度（脚本输出里的
  ds2），`对输入的梯度` 指传回主干网络的那份梯度（脚本输出里的 dx）——后者错，
  意味着**整个网络穿过这个模块的梯度都被污染**。

### 3.6 检查点与梯度范数

- **检查点（checkpoint）**：训练定期保存的完整参数与优化器状态。本任务每 2000 步
  一份。崩溃点 1088 在第一份之前，所以 iter_2000 是"崩后 912 步"的状态——用它推断
  崩前饱和度是**保守下界**（崩后饱和带还在，见 5.5）；
- **梯度范数**：把所有参数的梯度拼起来求总长度。健康训练约 0.5 上下；本任务崩溃后
  反复冲到 1e9~1e11，即所谓梯度爆炸的度量。

## 四、诊断过程（六步，每步：动机 → 做法 → 结果 → 结论）

### 第一步：全量前向+反向对拍平台（`parity_fused_bwd.py`）

**动机**：先确认算子在常规域是否可信，并系统排除偶发性因素。

**做法**：14 个前置算子场景（基线 + 缩放幅值/退化输入扫描：输入缩小 1e-4、放大 10
倍、偏置 ±50、批大小 2 等）+ 5 个后置算子场景；每次同时算前向与反向、与双精度参考
对拍；每场景连调两次验证逐位确定；另做 2000 次重复计算（soak）观察偶发坏值与漂移。

**结果**：

- 常规域前置算子**干净**：对输入的梯度相对误差 2.9e-3，正好是 bfloat16 地板；
- 缩放标量到 5 以上时，对缩放的梯度相对误差冲到 ~1；
- **后置算子（aclnnMhcPost 及其反向）全部场景干净**（1e-7~3e-3）；
- 2000 次重复零 NaN、零漂移，每次逐位相同。

**结论**：排除偶发坏值、不确定性、后置算子、退化输入；锁定嫌疑为**前置算子的反向
× 大幅值缩放**。

### 第二步：判别"算子缺陷"还是"数学本身病态"（`parity_scale_cliff.py`）——方法论上最关键的一步

**动机**：必须回答一个反问——也许 sigmoid + Sinkhorn 这套公式在饱和区**本来就没法**
用有限精度算（数学固有病态），那算子就没错，错的是参数化方案。

**做法**：三臂对照，同一个双精度参考、同一批量化输入：

| 臂 | 实现 | 对应 |
| --- | --- | --- |
| 融合算子 | aclnnMhcPreSinkhorn（训练走的路径） | `use-fused-mhc: true` |
| NPU 单精度 | 同样公式逐条算，float32，在加速器上 | `use-fused-mhc: false` 的回退路径 |
| CPU 单精度 | 同上，在 CPU 上 | 纯算法条件性，排除硬件 |

**结果**：两个单精度臂在**全部场景（含最深饱和）**保持 1e-6~1e-4；融合算子臂的
对 s2 的梯度从 z≈3 开始劣化（8e-2），z≈5 起达 0.2~67，且系统性偏置与相对误差同号
（单方向错误）；对输入的梯度恶化到 5~8e-2（单精度臂只有 2~3e-3）。三个随机种子
结论一致。

**结论**：**缺陷在算子的反向实现，不是数学病态**。同样的数学、同样的饱和输入，
逐条公式用单精度就能算对。

### 第三步：8 个 token 的最小复现（`minrepro_pre_sinkhorn_ds2.py`）

**动机**：把触发条件收缩到只剩一个变量，得到可提交给算子团队的、无运气成分的复现。

**做法**：序列长度 8，唯一扫描变量是 z 幅值。两组解耦实验：一组放大缩放标量 s2，
另一组把权重放大 10 倍而缩小 s2——如果两组在相同 z 处表现相同，触发器就是 z 本身
（softmax 饱和度），而不是"哪个参数大"。

**结果**（对 s2 的梯度，算子相对双精度参考）：

| z 幅值 | 相对误差 | 现象 |
| --- | --- | --- |
| ≤ 4 | ≤ 3e-4 | 正常 |
| 6.6 | 3.4e-2 | 开始错 |
| 26 | 2.15（**反号**） | 符号翻转 |
| 65 | **74**，且对输入的梯度相对误差 0.93 | 完全错误 |

两组解耦实验表现一致，确认触发器是 z 幅值。脚本可导出最坏 case 的全部张量
（`worst_ds2_case.pt`）。

**结论**：阈值定量化——**z ≳ 5 起错，z ≳ 20 反号**；这是后续与云端检查点对照的
"毒区标尺"。

### 第四步：崩溃 run 日志取证

（结果即 2.2 节的表格。）确认：崩溃精确发生在 1086→1088 之间；全程零 NaN 零跳过
（解释了为什么训练框架的保护机制没拦住）；崩后永不恢复。学习率此时已按余弦计划
从峰值下降、无异常。

### 第五步：崩溃 run 检查点取证（`ckpt_z_analysis.py`）——闭环

**动机**：以上都是离线构造的输入。最后一步要证明**云端崩溃任务的真实参数就落在
毒区里**，且算子在这些确切参数值上此刻就产出错误梯度。

**做法（a）饱和度轨迹**：对每份检查点，按 3.4 公式计算全部 56 个模块的 zmax_est：

| 检查点 | 中位数 | 最大值（模块） | 超过 5 的模块数 | 超过 10 | 超过 20 |
| --- | --- | --- | --- | --- | --- |
| 2000 步（崩后 912 步） | 2.01 | **22.02**（第 19 层注意力） | **14/56** | 6 | 1 |
| 6000 步 | 3.06 | 14.65 | 14/56 | 3 | 0 |
| 14000 步 | 3.26 | 14.21 | 15/56 | 3 | 0 |
| 25000 步 | 2.94 | 15.62 | 9/56 | 2 | 0 |

第一份检查点里就有 14 个模块越过"起错阈值 5"、1 个越过"反号阈值 20"——考虑到这是
崩后 912 步的保守快照，崩溃当刻的饱和度只高不低。崩后四份检查点始终有 9~15 个模块
泡在毒区，与"loss 卡在 7 平台、梯度范数反复爆炸"互为因果。

**做法（b）真实参数直接对拍**：取 2000 步检查点中饱和度最高的 6 个模块 +
2 个几乎未饱和的对照模块，把它们**原样的 hc_fn / hc_scale / hc_base** 分别喂给
融合算子与双精度参考（同一批随机 bfloat16 激活；激活尺度不影响结论，见 3.4）：

| 模块 | zmax_est | 对 s2 的梯度：相对误差 | 对输入的梯度：相对误差 |
| --- | --- | --- | --- |
| 第 19 层注意力 | 22.0 | **34.5 倍，符号翻转** | 0.147 |
| 第 17 层注意力 | 15.6 | 1.85 倍，符号翻转 | 0.116 |
| 第 24 层多层感知机 | 13.5 | 2.18 倍，符号翻转 | 0.074 |
| 第 16 层注意力 | 11.4 | 1.12 倍，符号翻转 | 0.042 |
| 第 10 层注意力 | 11.4 | 0.13 | 0.007 |
| 第 18 层多层感知机 | 10.3 | 0.088 | 0.032 |
| **第 0 层注意力（对照）** | **0.00** | **6.6e-5** | 3.4e-3（bfloat16 地板） |
| **第 27 层注意力（对照）** | **0.34** | **6.0e-5** | 2.1e-3（bfloat16 地板） |

**结论**：同一份检查点内，错误程度随 zmax_est 单调上升（完美的剂量-响应关系），
z > 11 的模块梯度全部达到反号级错误，而 z ≈ 0 的模块干净到 1e-5 量级。**云端生产
参数此刻就坐在离线实验划定的毒区里**——不是"可能会踩到"，是"已经踩着"。

### 第六步：算子源码级根因定位（`decompose_pre_sinkhorn_bwd.py`）——错误从哪来

前三步证明了"算子反向在饱和时错"，这一步回答"错在哪一行逻辑"。算子源码在本地
ops-transformer 克隆中（gitcode.com/cann/ops-transformer，`mhc/` 目录与 v9.1.1
tag 一致，即 CANN 9.1.1 libopapi 内置版）；反向核心是
`mhc_pre_sinkhorn_backward/op_kernel/mhc_pre_grad_kernel.h` 中的 SinkhornGrad
递推。三步排除法：

**（a）前向保存的中间量是不是错的？——不是。** 前向算子以 needBackward 模式
运行时会把它存给反向的全部张量（sigmoid 门、归一化前的混合系数、RMS 倒数、
40 个归一化分母、40 个归一化矩阵）一并输出。用双精度参考逐槽对拍（极端饱和
case）：全部一致（混合系数 1.1e-4、sigmoid 门 3e-6、softmax 矩阵 7.8e-6、
39 个分母与全部矩阵 ≤6.6e-7）。顺带解码了保存布局：矩阵只在偶数槽保存"行
归一化后"的版本，奇数槽是零占位（反向从不读取）；槽 1 的分母保存时不含 eps
（kernel 侧补加）。

**（b）把"数学上正确"的保存量替换喂给反向，错误会不会消失？——不会，逐位不变。**
单独调用反向算子，分别用算子自己的保存量与全真值保存量：输出的错误梯度完全
相同（对 s2 的梯度 0.33540 对 0.33533）。毒不在"前向存了什么"。

**（c）按源码的精确 fp32 运算顺序在 CPU 上重执行同一递推，能不能复现错误？
——能，复现到 0.02%。** SinkhornGrad 的公式逐行推演是正确的（包括用"除后
矩阵 + 单次除行和"的代数等价形式、eps 补偿、末尾的 4×4 转置搬运）。但把它
的运算序（对载入的分母补 eps → 除 → 乘矩阵 → 列/行归约 → 除分母平方 → 相减，
共 39 个半步）用 fp32 在 CPU 上照抄执行：得到对 s2 的梯度 = 0.33533，与 NPU
算子输出的 0.33540 吻合到万分之二；同一递推用 fp64 执行得到真值 0.023715。

**根因**：反向需要在饱和（近 one-hot、非主元全部压在 1e-6 的 eps 地板上、
部分列分母低至 4e-3）的矩阵上，串 39 步"除完再减"的链。每一步的减法都是
大数相消，fp32 的 7 位有效数字逐步耗尽，误差以乘性级联放大到 10 倍量级并
可反号——公式正确、输入正确、精度不够。低饱和时矩阵近均匀、每步良态，fp32
误差 1.7e-4，与前四步观测到的完整剂量-响应完全自洽。前向之所以永远正确，
是因为它只做除法，没有相减相消。修复方向是递推内部改用 fp64 或补偿求和；
我方规避即结论摘要中的两个过渡方案。

**方法论注记**：这一步曾一度得出"前向保存了错误的中间量"的假结论，原因是
本机 torch_npu 构建的 `torch.einsum` 在特定下标标签组合下给出静默错误的结果
（同一缩并 `F.linear` 精确、换组标签也精确）。所有参考实现已改为
`F.linear`/`matmul`，今后在本机做数值对拍一律不用 einsum。

## 五、崩溃机制：完整因果链（每一环都有实证）

1. **零初始化**（代码 `torch.zeros`，已核对）：训练开始时 hc_scale、hc_base 全 0，
   z_res 恒为 0，算子反向完全正确——所以前 1000 步训练正常，loss 平滑降到 2.28
   【代码 + 日志】；
2. **hc_fn 权重随训练增长**：行范数变大，zmax_est 从 0 逐步爬升；第一批模块越过 5，
   它们的对 s2 / 对权重 / 对输入的梯度开始带系统性偏差【第一、二步实验】；
3. **正反馈成形**：错误梯度继续改写权重，饱和度进一步变化，最强模块越过 20 进入
   反号区【第三步实验的阈值】；
4. **第 1088 步总爆发**：单方向错误梯度积累突破稳定域，loss 两步内 2.38 → 4.13 →
   8.50 → 11.71，梯度范数 0.49 → 195【日志取证】；
5. **永不恢复**：前向始终正确（模型还能正常算 loss），但 14~15 个模块持续泡在毒区，
   每步都在吃错误方向的梯度，loss 卡 ~7 平台，梯度范数反复冲 1e9~1e11【四份检查点
   的饱和度轨迹 + 日志】。

## 六、常见疑问逐条回应

1. **为什么 NaN 检查没拦住？** 缺陷输出的是"方向错误的有限值"，不是非有限值。全程
   25000 步 0 次 NaN、0 次跳过（日志统计）。
2. **为什么崩前毫无先兆？** 前向在所有输入下始终正确；训练监控的 loss / 准确率都
   只看前向。唯一的前兆藏在权重里（zmax_est 爬升），目前无人监控它。
3. **为什么不是数据 / 学习率问题？** 同数据同环境，仅不开 MHC 就不崩；且崩溃形态是
   两步内有限值跳变，不是坏样本或学习率过大常见的缓漂 + NaN 形态；学习率彼时正按
   余弦计划正常下降。
4. **为什么 loss 崩后不恢复？** 见五-5：错误梯度源（毒区模块）持续存在，优化器在
   错误地形里出不来。
5. **为什么记得是 ~1500 步，实测是 1088？** 云端看到的告警/人眼注意到异常通常晚于
   发生时刻；日志逐行解析给出的跳变点是 1086→1088 之间。
6. **离线对拍用的是构造输入，凭什么对应云端？** 第五步 (b) 用的是云端检查点里的
   真实参数值，不需要任何构造——剂量-响应直接成立。
7. **头部模块 hc_head 受影响吗？** 不受。它是只有 4 路 pre 门的头变体（缩放 1 个、
   偏置 4 个、权重 4×4096，无连接矩阵通道），不经 Sinkhorn 反向（检查点张量形状
   已核实）。
8. **后置算子 aclnnMhcPost 有问题吗？** 没有。第一步的 5 类场景（含批大小 2、
   近置换连接矩阵、饱和后置门、大残差）全部干净。

   `worst_ds2_case.pt`、本报告第四节证据链。要点：`aclnnMhcPreSinkhornBackward`
   在残差头 softmax 饱和（|z| ≳ 5）时反向输出错误（≳ 20 符号翻转），前向正确；
